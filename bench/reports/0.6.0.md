# 0.6.0: where every point came from

The road from 0.5.0 to 0.6.0, measured step by step. Every phase adds its numbers here, so
the release can show what each change was worth, and what it was not.

All runs are the `bench` workflow on GitHub's `ubuntu-latest` (4 cores, Node 24.21.0),
started 2026-10-08. Every number is relative to a bare node:http server doing the same
work **in the same run**: the runners differ from one another by up to two and a half
times, and only the ratio survives that.

## How it is measured

- **HTTP** (`run.mjs`): req/s next to node:http, the median of the rounds; the score is the
  geometric mean over the twelve scenarios. Higher is better.
- **CPU** (`cpu.mjs`): CPU microseconds the server spends per request, the lowest of the
  rounds, as server/node × 100. Lower is better.
- **Alone** (`inproc.mjs`): inkan without a network, microseconds per request through
  routing, validation and the answer. It sees the framework's own cost, which over HTTP is
  only a few microseconds on top of about eleven for Node's HTTP stack.
- Three runs per side; a table shows the median of the runs and, in brackets, their spread.

From phase 1 on, a change is measured against main **in the same run**: the workflow checks
main out next to the branch and runs it as the server `inkan-base` (`-f base=main`). The
first phase 1 runs, on their own runners, showed why: Fastify, unchanged, moved from 111 to
117 between them, more than the change being measured.

### What the profiles said

CPU and allocation profiles of the bench app under load (`--cpu-prof`, and allocation
sampling that keeps collected objects), next to node:http and Fastify:

- **hello**: inkan allocated about 9.0 KB per request, Fastify 7.8 KB, node:http 7.3 KB.
  inkan's own part was about 2 KB: the request id (`randomUUID`, also about 4 µs of CPU), the
  context with its default objects and closures, the input check's lists and closures.
- **big JSON body**: about a quarter of inkan's time goes to walking the schema
  (`ObjectSchema.check`, `EnumSchema.check`, `ArraySchema.check`); Fastify's compiled check
  barely shows next to its `JSON.parse`.
- **big answer**: more than half of inkan's time goes to `fits` and `_ser`, and
  `Object.keys` for every object allocates about 16 KB per answer.

## Phase 1: fixed costs

A request id from a counter, what a request worked out again worked out once at build,
a request with a body routed once, and nothing made for what a request never reads.

The CPU bench over HTTP, on its own runners, could not tell this change from the noise
(see "How it is measured"); the same-run comparison follows.
