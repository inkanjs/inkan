# 0.7.0: where every point came from

## 0.7.0

The perf phases of 0.7.0, measured one at a time against v0.6.0, and what each was worth,
and what it was not. These are local numbers: the GitHub runner numbers of the `bench`
workflow, the ones 0.6.0 was judged by, are still to come before the release, and the
release claims nothing until they are in.

### The machine and the method

- One laptop: Windows 11, Intel Core i7-1265U (2 performance cores with two threads each,
  8 efficiency cores), Node 26.7.0, with other work running on it. Measured unpinned, the
  same code twice (A/A) differed by up to 2× per scenario: the scheduler moves a process
  between performance and efficiency cores, and other processes come and go.
- So every bench ran pinned to one performance core (`start /affinity C` for `inproc.mjs`,
  `4` for `schema.mjs`; servers with `PIN=12`, the load generator kept off that core).
- **Alone** (`inproc.mjs`, the main instrument): every scenario of the HTTP bench, each in
  a process of its own, a round each; both sides live in that one process, each with its
  own code, and take turns in 20 short batches, so a busy moment slows both alike. Shown:
  µs per request of the lowest batch, the median of the rounds and in brackets their
  spread; and branch ÷ base × 100 batch by batch, median of the rounds (lower is faster).
  An A/A run (v0.6.0 against itself, 7 rounds) came out at **101.6** geomean, scenarios
  between 97.6 and 109.7: a change under about 5 % in one scenario is not a result.
- **Schema** (`schema.mjs`, new): ns per call of `_into`, the fit test and the writer on the
  bench's own data, lowest of seven repeats, median of five rounds per side. A/A within ±3 %.
- **CPU over HTTP** (`cpu.mjs`, pinned): only a confirmation. Node's HTTP stack on Windows
  costs 40–70 µs per request here, 2–3× the Linux runners, and the rounds spread by
  20–50 %, so it can rule out a large regression but not show a 5 % gain.
  `run.mjs` (req/s) was worse still (node:http itself between 6k and 19k req/s) and was not
  used to decide.

### Phase 0: instruments

`inproc.mjs` covers all ten scenarios (bulk body of 50, big answer, router 400, 3
middlewares, async, 404, 400 added) with the interleaved A/B above; `schema.mjs` is new;
`run.mjs` and `cpu.mjs` take `ONLY=` and `PIN=`; `servers.mjs` has `inkan-noid`, a
diagnostic server without request ids. No product code changed.

**The async scenario**, profiled under load (60k requests, `--cpu-prof`, `--trace-gc-nvp`):

| | allocated per request | scavenges per 10k | promoted per 10k |
| --- | ---: | ---: | ---: |
| node:http | 7.9 KB | 21–24 | 28–29 KB |
| Fastify | 8.3–8.8 KB | 6.0–6.5 | 33–36 KB |
| inkan 0.6 | 9.2–9.3 KB | 7.3–11.8 | 29 KB (one run 544) |

No mark-compact in any run. inkan's own functions are 4.5 % of the server's busy CPU;
the rest is Node (on Windows 38 % in `writev` alone). Nothing in inkan stands out and the
GC is not where the gap is: inkan makes about 0.6 KB more per request than Fastify and
promotes no more. Phase 5 therefore changed nothing.

**Request ids** (`inkan-noid`, hello): CPU per request 66.6 µs without ids, 70.2 with,
node:http 70.2 in the same run: within the noise. The counter id of 0.6.0 costs nothing
measurable; it does not explain hello at 10 connections.

### Phase 1: objects check by their own keys — kept

`ObjectSchema`'s stamp walks the value's keys with for-in and checks a field when its key
comes in the contract's order, reading it as `input[k]` (a plain load from the for-in's
cache); a field that comes elsewhere or not at all is read by its name. Every field is
still checked exactly once, in the contract's order, with `input[key]`, so no fallback and
no second run are needed: values, issues and their order stay the same by construction,
refine and transform included. The fields' checks are called directly (`_checker()`), as
is an array's item check. New equivalence test: keys out of order, missing, extra,
inherited, not enumerable, `__proto__`, null prototype, strict and passthrough.

| v0.6.0 → phase 1 | schema (ns) | | alone (µs) | |
| --- | ---: | ---: | ---: | ---: |
| bulk body (50) | 7930 → 6028 | 72.7 (70.2–76.0) | 26.06 → 23.28 | 89.5 (85.5–101.2) |
| small body | 103 → 69 | 66.7 (61.6–71.8) | 2.24 → 2.25 | |
| 400 | 180 → 143 | 81.5 (78.4–88.2) | 6.09 → 6.12 | 101.5 (97.5–102.6) |
| params `{id}`, coerced | 72 → 55 | 76.2 (74.4–79.3) | | |

The bulk body's lowest batch is better in every round (22.49–23.79 against 25.43–26.25), so
the gate (≥5 % in all rounds, nothing worse, 400 not slower) holds. Async read 104.5 in
the first run; 15 rounds of it alone: 100.4 (91.8–112.2). Over HTTP the bulk body was
65.9 against 68.3 µs (medians of 5), inside the spread.

### Phase 2: a parsed body handed on as it is — dropped

On the request path only, a body inkan parsed itself is returned as it is when it already
is what its schema makes of it (same keys in the same order, nothing coerced or
defaulted), instead of copied; `parse` and `safeParse` still copy. Limited to schemas with
no refine, transform or lazy inside, so a value that turns out not to fit can be checked
again the usual way without running user code twice.

Alone it worked: `_into` of the bulk body 6.0 → 3.1 µs, the bulk request 25.70 → 20.20 µs
(79.3, 77.6–80.6) against v0.6.0, about 12 points more than phase 1. Over HTTP, against
phase 1 in the same run, the bulk body was 71.4 against 69.6 µs (medians of 9; spread
61.7–79.8 and 65.2–79.9): no win beyond the spread, which was the gate. It also cost the
other checks 5–10 ns (the flag set around every `_into`), and the 400 path went 6.15 →
6.25 µs. Dropped; the code is parked on the local branch `perf-0.7-owned` (with an
equivalence test of every case owned against the walker) for the runners to judge, where
HTTP is three times cheaper and 3 µs would be 10 % of a bulk request.

### Phase 3: answers fit without `Object.keys` — kept

The object fit test walks the answer with for-in: in the contract's order one comparison
per key, else a map. A declared field the for-in did not see has to be one the trim leaves
out too (`propertyIsEnumerable`), so a non-enumerable field is still trimmed and written.
Since a for-in also hands out keys lent by Object.prototype, the serializer asks the fit
test nothing when Object.prototype has an enumerable key (one for-in over it per answer).
Two new pinning tests; both fail without those two guards.

Router 400 and middleware read 110.3 and 106.2 in the first run; 11 rounds of them: 96.9
and 99.4, lowest batches 1.93 against 2.01 and 1.91 against 1.92. Over HTTP the big answer
was 94.9 against 121.8 µs (medians of 7). Kept.

### Phase 4: middleware in one frame — kept

`App.later()` ran its work in an inner async closure made per request, wrapped by
`deadline`. Now the route without a timeout runs body, middleware and handler in the
frame of `later` itself; a route with a timeout races `work()` against the clock as
before. A method instead of the closure, still two frames, gained nothing (101.2); the one
frame did. New test: a timeout counts the route's middleware too.

| phase 3 → phase 4, alone | µs | ratio |
| --- | ---: | ---: |
| 3 middlewares (9 rounds) | 1.92 → 1.82 | 96.2 (80.0–117.8) |
| 3 middlewares (11 rounds) | 1.91 → 1.81 | 94.9 (83.3–118.7) |
| hello, async | unchanged | 101.6, 96.3 |

Lowest batches 5 % better in both runs (the gate was 3 %). Over HTTP 43.5 against 45.1 µs
(medians of 7), the same direction, inside the spread.

### Phase 5: async — nothing

The profile (phase 0) points at nothing of inkan's: 4.5 % of the CPU, no GC difference
worth a change. The one async frame left (`settle`) is the handler's own promise.

### Forecast

Locally, inkan itself is a few µs of a request that costs Node 40–70 µs on this machine,
so the HTTP numbers here say nothing about the gate. From the alone and schema numbers,
scaled to the runners, where Node's stack is about three times cheaper:

- **big JSON body**: −7 to −10 % alone, about 2–3 µs of a ~25 µs request on a runner: the
  80.7 of 0.6.0 might reach 83–85. Fastify had 89.8, so still behind. The parked phase 2
  would add about as much again, if the runners can show it.
- **big answer**: −7 % alone, −23 % to write. inkan was already ahead (77.4 against
  Fastify's 72.8) and gains.
- **3 middlewares**: −5 % alone, perhaps 87.0 towards 89 over HTTP; Fastify had 93.6.
- **hello, params, router, async, 404, 400**: unchanged. What separates them from Fastify
  is not in inkan's own code as far as these benches see (async: 4.5 % of the CPU, no GC
  difference).

So the geomean may move one or two points, from 89.1 to about 90–91 against Fastify's
88.6, still inside the spread of three runner runs. The honest forecast is "level with
Fastify, ahead a little more often", not "faster than Fastify". The runners decide before
the release.

The gate, as set in 0.6.0:

1. **inkan above Fastify, outside the spread: met.** 90.3–92.2 against 87.4–88.1, ahead in
   every run, by 2.6 to 4.1 points.
2. **inkan above Fastify in every scenario: not met.** Fastify still leads the async handler
   (103 against 97) and hello at 512 connections (97 against 89, a wide spread on both);
   3 middlewares are level (91 against 90). The big JSON body is level at 95.
3. **No scenario worse than 0.6.0: met.** Every median is at or above inkan-base; the single
   low points (params + query 80 in run 3) are the runner, not the code, since run 1 and 2
   have inkan at 96 and 108 there.

So the claim is: **faster than Fastify on this bench, on average, without runtime code
generation; not in every scenario.** About 5 % faster than 0.6.0 (91.4 against 86.7).
