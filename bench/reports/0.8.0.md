# 0.8.0: where every point came from

## 0.8.0

The two scenarios Fastify still led on the runner at 0.7.0: the **async handler** (Fastify
103 % of node:http, inkan 97 %) and **hello at 512 connections** (97 against 89, a wide
spread on both). Local numbers again; the runners decide.

### The machine and the method

The same laptop as in 0.7.0 (i7-1265U, Windows 11, Node 26.7.0), busier than then: hello
alone took 1.4–2.5 µs where 0.7.0 measured 1.33, and an A/A of the same code spread by
±10–15 % per round. Everything ran pinned to one performance core (`start /affinity C`).

- **Alone** (`inproc.mjs`) as in 0.7.0. It goes through `inject()`, so it never sees what
  the Node server path does after `handle()`.
- **Server path** (new, a scratch script): `app.listener` with a stand-in `req`/`res`, 100
  requests in flight, the next one started from `setImmediate` as a socket would; both sides
  live in one process and take turns in 20 batches, like `inproc.mjs`. This is what `listen`
  runs, without the sockets. A/A: 99.6 (92.2–112.1) and 102.6 (83.9–111.8).
- **Allocation**: `v8.getHeapStatistics().total_allocated_bytes` around 20 000 requests of
  the server path, lowest of 5.
- **Under HTTP** (`--cpu-prof`, `--trace-gc-nvp`, autocannon) only to look, not to decide:
  `cpu.mjs` gave node:http 95.9 µs for hello against Fastify 76.7 in one run.

### The async handler — kept

**What inkan did that Fastify does not.** Fastify puts one `then` on the handler's promise
and writes the answer in it (`wrapThenable`). inkan had `settle()`, an async function
(`respond(await pending)`), whose own promise `pass()` waited on with a second `then` and
two closures: one async frame, one promise and one turn of the microtask queue more per
request. The deadline is not in the way (no timeout: the work is handed back as it is), and
onSend/onResponse are not on this path (a route with hooks takes `full()`).

The plumbing alone (an `async` handler that awaits once, K = 100 in flight, interleaved,
3 runs, ns per request, lowest batch):

| | run 1 | run 2 | run 3 |
| --- | ---: | ---: | ---: |
| async `settle` + `then` in `pass` (0.7) | 373 | 435 | 327 |
| `settle` with `then`, no async frame | 321 | 373 | 283 |
| one `then`, written there (Fastify) | 223 | 245 | 203 |

**The change.** `settle()` puts one `then` on the handler's promise. On a Node server
(`raw.res`) it writes the answer right there and `handle()` returns nothing; `pass()` has no
promise to wait on. Elsewhere (`inject`, `fetch`, `exchange`) it returns that one `then`.
With `context: true` the answer is still written by `pass()`, outside the request's store,
as every other answer is. A log or logger that throws still answers 500 through `broken()`.
New test: an async handler over a real socket, plain, with `context` and with a logger that
breaks: the answer, the trimmed body, the problem, HEAD, `reply()` headers.

| v0.7 → 0.8, server path, 11 rounds | µs | ratio |
| --- | ---: | ---: |
| async (run 1) | 1.40 → 1.29 | 91.1 (78.4–97.2) |
| async (run 2) | 1.52 → 1.46 | 90.6 (78.4–103.1) |
| async (run 3, final code) | 1.42 → 1.22 | 86.7 (80.5–101.4) |
| hello | 0.71 → 0.74 | 99.9 (76.8–114.6) |
| params + query | 1.36 → 1.40 | 99.8 (92.0–118.1) |

31 of 33 async rounds below 100, the lowest batch better in all three runs. Allocated per
async request: 3661 → 3190 bytes (−13 %); hello 1488 → 1473. Alone (`inject`, which only
loses the async frame): async 96.1 (87.4–116.5), the rest 98–105, inside this machine's A/A.

**What it is worth.** About 150 ns and 470 bytes per async request. Under HTTP on the
runners a request costs some 20–30 µs, so this is perhaps 0.5–1 point of the async score,
not the 6 that separate inkan from Fastify. The profile under load (Windows, 100
connections) shows nothing else of inkan's in the way: all of src/ is 6.3 % of the busy
CPU, `writev` alone 58 %; the largest items are the router (1.3 %, against 0.7 % for
find-my-way) and the writer (1.1 %). params + query, which shares the router and the
coercion, is level with Fastify on the runner (96 against 95), so they do not explain the
async gap either. inkan allocates about 1.1 KB more per async request than Fastify over
HTTP (9.2–9.3 KB against 8.0–8.2) before this change.

### Hello at 512 connections — nothing changed

**How inkan writes** is how Fastify writes: one `writeHead(status, headers)` with the
content length set, then `end(body)` (which corks and sends headers and body in one write);
no `setHeader`, no second write, Node's own Date and keep-alive. What differs on the wire:

- inkan sends `x-request-id` (25 bytes and one header line more per answer);
- Fastify sets `keepAliveTimeout` to 72 s (`Keep-Alive: timeout=72`), inkan keeps Node's 5 s.
  Under a steady load no connection idles that long, so it should not count here.

**What changes at 512** is the garbage that outlives a scavenge (`--trace-gc-nvp`, 6–8 s
of hello, per 10 000 requests, two runs each):

| | survived KB | promoted KB | scavenge pause ms | allocated B/req |
| --- | ---: | ---: | ---: | ---: |
| 10 connections: node / fastify / inkan | 37 / 17 / 21 | 16 / 16 / 15 | 14.8 / 1.8 / 3.1 | 7097 / 7071 / 7405 |
| 512: node:http | 575–615 | 63–321 | 4.4–4.7 | 6867–7243 |
| 512: Fastify | 480–498 | 356–369 | 2.9–3.3 | 7500–8160 |
| 512: inkan | 1187–1277 | 1048–1110 | 4.5–5.2 | 7595–7841 |
| 512: inkan without request ids | 813–843 | 697–703 | 3.2–3.7 | 6588–7098 |

At 10 connections all three keep the same; at 512 inkan keeps about 2.5 times what Fastify
keeps across a scavenge and promotes three times as much, and request ids are about 40 % of
that difference. What else an answer waiting for its write keeps alive was not found
(heap snapshots under load show no inkan objects in flight; the body inkan writes is a flat
string, Fastify's a cons string). Worth perhaps 0.2 µs per request in scavenges here, more
once the promoted bytes cost a mark-compact in a 15 s run. Request ids are a default and
stay; whether they are the 512 gap is for the runner to say (`inkan-noid` is in servers.mjs).

### Parked: a parsed body handed on as it is (`perf-0.7-owned`) — still parked

Cherry-picked onto 0.8 (`scratch/owned-0.8`, clean, typecheck and tests green). Against
0.8 without it:

| | owned | 0.8 | ratio |
| --- | ---: | ---: | ---: |
| schema: `_into` bulk body as a body (ns) | 3669 | 6825 | 49.5 (46.8–63.6) |
| schema: `_into` params `{id}`, coerced (ns) | 72 | 60 | 117.3 (110.3–162.3) |
| schema: `_into` 400 body (ns) | 175 | 166 | 106.0 (86.0–136.1) |
| alone: bulk body (50) (µs) | 26.53 | 30.24 | 86.1 (74.2–123.1) |
| alone: 400 (µs) | 7.39 | 7.61 | 107.1 (97.6–133.5) |

Again 3 µs off a bulk body, about half its check; again a few ns on every other check
(params +12 ns, all rounds worse). Over HTTP this machine cannot tell (`cpu.mjs` put the
unchanged 400 at 88 against 126 µs between the two sides). On a runner 3 µs would be about
10 % of a bulk request. It needs the runner: keep it if big JSON body moves by more than its
spread and params + query and 400 do not drop.
